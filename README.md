# Local Service Lead-Gen Template

A config-driven static website template for local service lead generation
(rank-and-rent). Plain HTML/CSS/JS — no build step, no framework, no
external fonts. Designed for GitHub Pages with a custom domain.

## Read this before publishing anything

- **`{ type: "marker" }` blocks render as a loud amber "Unfinished — not for
  publication" box on the page.** They exist so nothing you haven't sourced
  can accidentally ship invisibly. `node bake.js --check` fails while any
  remain in `config.js`.
- **Never just delete a marker to make the count go down.** Either fill it
  from a real, checkable source (see "Content-sourcing rules" below) or
  delete the claim it guards entirely. A marker is a promise that something
  is either true or gone — not a formatting nuisance.
- **`testimonials` and `photos` in `config.js` stay empty until a real
  business supplies real, verifiable content.** Never invent names, star
  ratings, review counts, or job photos — see "Real-evidence placeholders"
  below.
- **Schema stays `Organization` until a renter's real premises/hours
  exist.** See "Schema: Organization until a renter exists" below before
  ever touching `schema.type`.

**Swapping niche/city: edit [`config.js`](config.js), run `node bake.js`,
run `node bake.js --check`, commit the regenerated files.** `config.js` is
the only file you edit by hand — everything else is regenerated from it.
`bake.js` is a manual helper you run yourself — not a build pipeline;
nothing runs automatically and the deployed site stays plain static files.

## How it works

`bake.js` reads `window.SITE_CONFIG` from `config.js` and writes the finished
HTML — page content, brand colors, the lot. **It is the only renderer.**
`js/main.js` doesn't build the page; it only wires up the parts that need a
browser (form handling, nav toggle, GA4, scroll effects). So a copy or layout
change means editing `config.js` and running `node bake.js` — editing
`main.js` will not change how a page looks.

Each service page is mapped to a service by the `page` field on its config
entry (make it a keyword URL, e.g. `drain-cleaning.html` — not a numbered
stub); each area page is mapped by its `slug` (the file is `<slug>.html`). A
`.html` file on disk that `bake.js` doesn't generate is reported by `--check`
as orphaned — it would otherwise keep serving copy frozen at whatever config
said when it was last baked.

**What's baked into static HTML (i.e. essentially everything — crawlers see
it before any JS runs):** each page's `<title>`, meta description, canonical URL, Open Graph
tags, JSON-LD (`Organization` on every page — see below; `FAQPage` where
FAQs exist; `Service` + `BreadcrumbList` on service pages; `BreadcrumbList`
on area, about, and privacy pages), the H1, and the `<noscript>` fallback.

**Everything derived is regenerated by one command:**

```
node bake.js
```

That rewrites all page HTML **plus** `CNAME`, `robots.txt`, `sitemap.xml`
(built from the actual list of pages generated, so it can never drift),
`404.html`, and `favicon.svg` (brand color + shape from config). The only
static asset it doesn't generate is `images/og-image.png` — a neutral
illustration containing no business details.

**Before launch, run the preflight:**

```
node bake.js --check
```

It writes nothing and fails loudly (exit 1), reporting two separate
categories:

1. **Unfinished content** — every `[VERIFY: ...]`, `[NEEDS INPUT: ...]`,
   `[BUILD GATE: ...]`, or other `[UPPERCASE_TOKEN]` placeholder anywhere in
   `config.js`, and every `{ type: "marker" }` content block, whichever page
   it's on. Reported with the exact config path (e.g.
   `services[0].blocks[6].note`) so it's findable.
2. **Preflight problems** — template leftovers (`yourdomain`, `Springfield`,
   555-numbers, `YOUR_`, lorem ipsum, `TODO`/`TBD`/`FIXME`), unset
   `ga4Id`/`ingestUrl`/`ingestSecret`/`turnstileSiteKey`, broken/orphaned
   page files, sitemap/disk drift,
   domain mismatches, missing images or image dimensions, duplicate
   meta title/description, and banned LocalBusiness-only schema terms
   reappearing while `schema.type` is `Organization`.

Warnings (non-fatal) fire if `testimonials`/`photos` are populated, if
`business.phone` and `business.email` are both empty, if a `metaTitle` is
under 30 or over 60 characters, or if an image declares `widths` whose
variant files aren't on disk — reminders, not blockers.

**Author-voice guard.** Every string value in `config.js` is rendered to the
public site, so the preflight also flags working notes written to the
operator rather than to a reader: dated decision logs, "not urgent",
"no source found yet", cross-references like "already cited above", failed
research ("returned 404", "could not be found"), review-cadence instructions
("on a fixed schedule"), and — inside a `note` block only — the
`schema.founder` name. Those belong in a code comment, not in copy. The
patterns are deliberately narrow: a hit should mean real author-voice copy,
so if one fires on legitimate reader copy, reword the copy rather than
loosening the pattern.

## Content blocks (service pages)

Each service in `config.js` is an ordered array of typed **blocks** rather
than a fixed card layout, so real long-form copy — headings, data tables,
callouts, inline citations, per-service FAQs — fits without fighting the
template.

| Type | Shape | Renders as |
|---|---|---|
| `h2`, `h3` | `{ type, text }` | Section heading |
| `p` | `{ type: "p", text }` | Paragraph |
| `lead` | `{ type: "lead", text }` | Larger intro paragraph |
| `ul`, `ol` | `{ type, items: [...] }` | List |
| `table` | `{ type: "table", caption?, headers: [...], rows: [[...]] }` | Data table |
| `note` | `{ type: "note", text }` | Sourced callout/aside |
| `credit` | `{ type: "credit", text }` | Small citation line |
| `marker` | `{ type: "marker", text }` | **Loud unfinished box — see above** |
| `faqs` | `{ type: "faqs", items: [{ q, a }] }` | FAQ accordion — also builds this page's `FAQPage` schema |
| `form` | `{ type: "form", heading?, presetService?, extraField?, placeholders? }` | The quote form, embedded inline |
| `image` | `{ type: "image", src, alt, width, height, caption? }` | Figure — **no caption on illustrative/stock images** (a caption implies authorship of real work) |

`text` supports `**bold**`, `[label](url)`, and newlines — escaped first,
so config copy can never inject HTML.

FAQs live on the page that answers them: per-service questions go in that
service's own `faqs` block; general questions about quoting, payment, and
service area go in `about.faqs` (About & Contact page). There is no
standalone `faq.html` — each page's `FAQPage` schema is built from exactly
the FAQs actually present on it.

## Content-sourcing rules (for resolving markers)

1. Sources must be **named and checkable**: a local government, a heritage
   body, a standards document (cited by number, never reproduced if
   paywalled), a government agency, or a manufacturer's own technical page.
   Never a generic blog or marketing page standing in for one, even if it
   states a number.
2. **Verify every URL resolves before citing it.**
3. **Don't over-scope a source.** If guidance is scoped to a specific
   context (e.g. heritage construction), say so in the prose rather than
   presenting it as a general rule.
4. **If a marker bundles several claims and only some are sourceable, split
   it** — resolve the sourced part, leave a narrower marker for the rest.
5. **Explaining why no figure can honestly be given is a valid
   resolution** (e.g. "varies too much by property to state a number here").
6. **Markers needing real-world data collection (e.g. your own job/pricing
   history) cannot be closed by searching harder.** Recognize that early.
7. **An empty table reads as broken, not as "coming soon."** If you don't
   have real numbers for a pricing table, don't fill it with guesses or
   leave it empty — delete the table block and write an honest paragraph
   about what drives the price instead, backed by content you do have.
8. **Private author notes go in `/* TODO (Name): ... */` JS comments in
   `config.js`; reader-facing citations go in `note`/`credit` blocks.**
   `--check`'s TODO scan only looks at config string *values*, not JS
   comments — that's deliberate, so author notes don't block launch but
   also never leak to a visitor.
9. After every edit: `node bake.js`, then `node bake.js --check`, and
   confirm the unfinished-content count actually dropped.

## Schema: Organization until a renter exists

The default JSON-LD type is `Organization`, not a `LocalBusiness` subtype,
and stays that way until a real business is attached. A rank-and-rent site
pre-renter has no premises, no opening hours, no service counter, and no
reviews — a `LocalBusiness`/`AggregateRating`/`Review`/`priceRange` claim
would all be invented. `node bake.js --check` greps the baked HTML for
these terms and fails if they reappear while `schema.type` is
`Organization`, as a guard against a future edit quietly reintroducing
them.

**Upgrade path:** once a renter's real address and hours exist, set
`schema.type` to a real [LocalBusiness
subtype](https://schema.org/LocalBusiness) (e.g. `Plumber`,
`HomeAndConstructionBusiness`) and fill in `schema.priceRange` and
`business.hours`. The `--check` guard steps aside automatically once
`schema.type` isn't `Organization`.

## Unset config degrades to absent, never to broken

`business.phone`, `business.email`, and `business.hours` all ship **empty**
by default. Every place that would use them — header call button, hero
actions, footer, About & Contact contact lines, the mobile contact bar,
the 404 page, JSON-LD, and the form's error-fallback message — omits that
UI element while the field is empty, rather than rendering a dead link or a
fake-looking number. Fill each in only once it's real; the site adapts
automatically, no other edits needed.

The same principle applies to `testimonials`/`photos` (stay hidden while
empty) and `areas` (nothing renders or links until populated).

## Swap-niche checklist

1. Edit `config.js` (all the content lives there, top to bottom).
2. Run `node bake.js` to regenerate every derived file.
3. Run `node bake.js --check` and fix everything it flags — resolve every
   marker from a real source, fix every preflight problem.
4. Commit the regenerated files.

What to edit in `config.js`:

1. **business** — name, city, state, service area. Leave phone/email/hours
   empty until real (see above).
2. **domain** — used for canonical URLs, schema, OG tags, and to generate
   `CNAME`, `robots.txt`, and `sitemap.xml`.
3. **brand** — accent color, hover shade, contrast text color, plus the
   visual theme (`style` + `pattern` — see "Making each site look
   different" below).
4. **ga4Id** — **required before launch**: while it contains `XXXX`, no
   analytics and no `click_to_call` tracking, meaning no call-volume proof
   for a future renter.
5. **ingestUrl / ingestSecret / turnstileSiteKey** — form leads post straight
   to our own ingest endpoint (see `rank-and-rent-backend`'s
   `docs/DASHBOARD_PLAN.md`, Phase 2 Stage B), not to a third-party form
   service. `ingestUrl` is the endpoint, `ingestSecret` is the shared secret
   it checks, `turnstileSiteKey` is the Cloudflare Turnstile key for spam
   filtering. **Required before launch: the site cannot capture web form
   leads until `ingestUrl`/`ingestSecret` are real values, and has no spam
   protection until `turnstileSiteKey` is set.** Until then, submitting the
   form shows a polite error with the phone number as fallback — phone calls
   work, web leads are silently lost. Whichever services host the endpoint
   receive enquiry data, so name them in the privacy policy copy.
6. **schema.type** — leave as `Organization`. See the schema section above.
7. **pages** — meta titles/descriptions and message-matched headlines for
   home/about/privacy.
8. **services** — 3 to 5 entries, each an ordered `blocks` array (see
   above) plus its own keyword-URL `page` filename.
   - **Changing the number of services?** Add/remove entries; delete any
     now-orphaned page file (`--check` flags orphans); the sitemap updates
     itself on the next bake.
9. **areas** — 0 or more suburb/area pages, ships empty. Only add these
   once the core pages are live **and** each area has genuinely
   differentiated content — six thin suburb pages with the name swapped is
   the scaled-content pattern search engines filter out.
10. **about.faqs / howItWorks / about.paragraphs / contact.fields** — the
    site copy and the quote form's field list.
11. **images** — the homepage hero and each service have an `image` entry
    (`src`, `alt`, `width`, `height`). Drop new files into `/images` and
    update `src`/`alt` in config — no code changes.
    - Use optimized **JPG or WebP**, roughly 1200×800, ideally under
      ~150KB (there's no build step — optimize before committing, e.g.
      [squoosh.app](https://squoosh.app)).
    - Keep `width`/`height` accurate to prevent layout shift.
    - Write `alt` text that literally describes the image (good for
      accessibility and image SEO). Every rendered `<img>` also gets a
      `title` attribute — it defaults to `alt`, so you don't need to set
      anything, but add an optional `title` field on the image entry if you
      want the tooltip to read differently.
    - **Responsive variants.** An image entry may also carry
      `widths: [400, 560, 720, 960]` and a `sizes` string. That builds a
      `srcset`, so a phone downloads a 400px file instead of the full-size
      one — worth ~130KB per image on mobile. Each listed width needs a real
      file beside the original, named `images/<name>-<width>.<ext>`; resize
      them yourself (squoosh, or `npx sharp-cli`) and `node bake.js --check`
      warns if one is missing. Omit `widths` and the single full-size file is
      used as before. Note the full-size original is deliberately **not** a
      `srcset` candidate — leaving it in lets a high-DPR phone pick it over
      the variants, which is the exact waste the variants exist to prevent.
    - Illustrative/stock images carry **no caption** and no implication of
      authorship. Where an image would need to make a factual or
      diagnostic claim (e.g. "this is what a structural crack looks like"),
      draw it as an inline SVG `image` block asset instead of sourcing a
      photo that only approximately matches — a near-miss photo actively
      misleads.
    - The "Recent Work" (`photos`) section stays empty until a renter
      supplies real job photos (see "Real-evidence placeholders").

## Making each site look different

Every deployment can have its own look without touching CSS. Three knobs in
`config.js` combine into the theme, and everything else (tints, glows,
shadows, the footer color, even the favicon shape) is derived automatically:

1. **`brand.color` / `colorDark` / `colorContrast`** — the palette. One
   accent color drives the whole site: pale section washes, tinted borders,
   colored button shadows, and a matching dark footer are all computed from
   it by `bake.js` and baked into every page's `<head>`.
2. **`brand.style`** — the design personality:
   - `classic` — clean and trustworthy; soft gradient hero, rounded cards
   - `bold` — full-color gradient hero with a diagonal edge, pill buttons,
     heavy headings
   - `soft` — heavily rounded corners, pale tinted sections, blob-shaped
     imagery, rounded font (where the OS has one)
   - `sharp` — squared corners, hard borders, offset solid shadows,
     uppercase section headings
   - `elegant` — serif display headings, framed imagery, thin rules, quiet
     and premium
3. **`brand.pattern`** — a subtle background texture on the hero, page
   headers, and CTA band: `none`, `dots`, `grid`, `diagonal`, or
   `crosshatch`. Patterns are pure CSS gradients (zero requests).

The chosen style/pattern is baked onto the `<html>` tag and the derived
palette into each page's `<head>` by `node bake.js`, so the final look
renders on first paint with no flash and no JS required for styling.
`bake.js` (and `--check`) validate the values and fail loudly on typos.

A quick way to pick a combination: change `style`/`pattern` in `config.js`,
run `node bake.js`, and reload your local preview. The bake takes well under
a second, so you can flip through looks quickly — but it does have to run,
since nothing is applied at load time any more.

## Real-evidence placeholders (do not fake these)

`testimonials` and `photos` in `config.js` are **intentionally empty**. The
"What Customers Say" and "Recent Work" sections exist in the template but
stay hidden until these arrays contain real, verifiable content from an
actual operating business. Never populate them with invented names, star
ratings, or review counts — that's a legal/ethical liability (FTC fake
review rules) and gets renters angry when discovered. `node bake.js --check`
warns (doesn't block) if these are non-empty, as a reminder to double-check.

The same standard applies to pricing: don't invent a price range from
competitor sites or national averages. Leave pricing out of the config
(write about what drives the price instead — see content-sourcing rule 7)
until a renter's own quote history exists.

## When a renter signs

Consolidated checklist for everything deliberately deferred to a real
operator, so it doesn't have to be rediscovered one at a time:

- [ ] Add real `business.phone` / `phoneDisplay` / `email` / `hours`.
- [ ] Populate `testimonials` with real, verifiable reviews (name + real
      quote, never invented).
- [ ] Populate `photos` with real job photos from the actual business.
- [ ] Add real pricing (a `table` block or `note` prose) once quote history
      exists — see content-sourcing rule 7.
- [ ] Upgrade `schema.type` to a real LocalBusiness subtype and fill in
      `schema.priceRange` — see "Schema: Organization until a renter
      exists".
- [ ] Consider adding `areas` pages once there's genuinely differentiated
      per-suburb content to write.
- [ ] Run `node bake.js && node bake.js --check` and confirm clean.

## Deploy to GitHub Pages

1. Create a public repo and push all files to the root of the default branch.
2. Repo → Settings → Pages → Source: "Deploy from a branch" → your default
   branch, `/ (root)`.
3. Custom domain: put your bare domain in `CNAME` (GitHub fills the Pages
   setting from it), then point DNS at GitHub Pages:
   - `A` records for the apex: `185.199.108.153`, `.109.153`, `.110.153`, `.111.153`
   - `CNAME` record for `www` → `<username>.github.io`
4. Enable "Enforce HTTPS" once the certificate is issued.
5. Submit `sitemap.xml` in Google Search Console.

## Local preview

```
npx serve .
# or
python -m http.server 8080
```

Note: some static-file servers (including `npx serve` by default) strip
`.html` from URLs ("clean URLs"). GitHub Pages doesn't. Either way the pages
are plain static files, so both serve identically.

(Opening files via `file://` won't work reliably — the pages fetch nothing,
but browsers restrict some behavior on file URLs.)

## Why the pages look the way they do (performance and crawlability)

Four things in the generated HTML exist so the site loads fast on a phone and
reads fully to a crawler that doesn't run JavaScript. They're easy to undo by
accident:

- **The page content is baked, not rendered by JavaScript.** `bake.js` writes
  the real header, hero, page content and footer into every page at build
  time. Before this, a no-JS crawl of Perth Brickworks' two long service pages
  saw **39 and 49 words** against the ~6-10k a JS-rendering crawl saw.
- **The whole stylesheet is inlined** in each page's `<head>`. A linked
  stylesheet blocks first paint for an extra round trip. Edit
  `css/styles.css` as normal and re-run `node bake.js`.
- **The hero has no entrance animation.** `main.js` adds `html.anim` only
  after the page has painted, so a fade-in on hero elements would hide the
  headline and image and re-reveal them a moment later — and Google measures
  that later moment as Largest Contentful Paint. Below-the-fold content
  animates via `.reveal` instead, where the cost is zero.
- **Boot work is deferred one task** (`setTimeout(…, 0)` at the bottom of
  `main.js`) so `main.js`'s own synchronous block isn't occupying the main
  thread at the moment the browser would paint the already-baked hero.
  Deliberately *not* `requestAnimationFrame`: rAF doesn't fire for a tab that
  isn't compositing frames (backgrounded, prerendered, an unfocused preview
  pane), which leaves the page blank in exactly that case.

Because content is baked, **copy changes need `node bake.js`** to show up.

## Divergence from the template

If you change `bake.js`, `js/main.js`, `css/styles.css`, or the page-shell
structure for a specific build because real copy didn't fit the shape,
that's allowed — but record what you changed and why in your site's own
README under a "Divergence from the template" heading. It's the fastest way
to re-apply your changes if this template is ever regenerated, and the
fastest way for the next person to know your build isn't running the
stock engine.
